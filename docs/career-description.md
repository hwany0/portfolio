# 경력기술서

고객관리·청구·수금·결제·멤버십·매체사 업무 시스템을 개발하고 운영했습니다. Java/Spring 기반 백엔드와 외부 API 연동을 중심으로 인증·인가, 배치 처리, 데이터 정합성, 장애 분석 및 레거시 현대화를 수행했습니다.

주요 경험:

- 도메인이 분리된 서비스의 통합 인증, 토큰 재발급 및 MFA
- 데이터 불일치와 직렬화 장애를 재현·분석하고 대응 구조 개선
- 레거시 시스템 전환, 공통 UI 및 공통 설정 정비

- Java 17/Spring Boot 3.5.x 전환과 공통 API·예외·인가 구조 정비(진행 중)

## 2. 주요 프로젝트

### 2.1 옥외 광고 청약 시스템 SaaS 전환 및 공통 아키텍처 정비

- **기간:** 2026.09 ~ 진행 중
- **역할:** 백엔드 공통 구조 정비, 레거시 전환, 인증/인가 구조 설계 및 구현
- **기술:** Java 17, Spring Boot 3.5.x, Gradle, MyBatis, MSSQL, Thymeleaf

#### 배경 및 목표
기존 Java 8/Spring Framework 기반 업무 시스템을 Java 17/Spring Boot 3.5.x 기반으로 전환하고, 기존 업무 흐름을 고려하면서 공통 설정과 요청 처리 방식을 표준화하고 있습니다.

#### 수행 내용
- Java 17 및 Spring Boot 3.5.x 기반 실행 구조를 구성하고 Gradle/JAR 빌드 구조 정비
- 전자정부프레임워크 의존성을 확인하고 Spring Boot 표준 구성으로 대체하는 작업 진행
- JSP 화면의 Thymeleaf 전환을 위한 공통 렌더링 구조와 화면 데이터 제공 방식 정리
- 공통 API 응답 DTO, 전역 예외 처리 및 메시지 조회 구조 정비
- 조직 권한, 매체 권한, 사용자 그룹 권한을 구분하고 AOP 기반 공통 권한 검증 구조 설계·적용 중
- 메뉴 노출과 API 접근 제어를 별도 계층으로 구분하고, 요청 매체 ID와 사용자의 접근 가능 범위를 검증하는 정책 정리

#### 기술적 고려 사항
- 전체 업무 로직을 일괄 재작성하기보다 공통 설정과 요청 처리 기반부터 정비해 전환 범위를 통제
- 조직·매체·사용자 그룹 권한을 하나의 관리자 여부로 단순화하지 않고 API별 권한 요구사항을 구분
- 화면에서 메뉴를 숨기는 것만으로 보안을 보장하지 않고 서버 측 API에서 접근 권한을 검증

#### 상태
진행 중입니다. 전환 기반과 공통 구조를 정비하고 있으며, 화면 전환 범위 확대, 권한 정책별 테스트 및 회귀 검증은 진행 범위에 따라 이어갈 예정입니다. 완료되지 않은 항목을 완료 성과로 표현하지 않습니다.

### 2.2 J-Mobile AI Direct Routing 프로세스 구축

- **기간:** 2025.09 ~ 2025.12
- **역할:** AI UX, 서버 처리 흐름, 파라미터 및 권한 검증 구조 설계
- **기술:** Java 7, Spring Framework 4.2.1, JSP, WebToB, JEUS, vLLM API, Gemma-4, Speech Recognition

#### 배경
고객·독자 조회 후 수금이나 VOC를 처리하려면 여러 메뉴를 순차적으로 이동해야 했습니다. 현장 사용자의 메뉴 탐색과 입력 부담을 줄이기 위해 음성 명령으로 업무 화면에 진입하는 Direct Routing 구조를 설계했습니다.

#### 수행 내용
- 어느 메뉴에서나 음성 입력을 시작할 수 있는 FAB 기반 진입 UX와 처리 흐름 구성
- `VoicePromptGenerator`에서 메뉴·파라미터·행위 정보를 LLM 프롬프트에 제공
- `VoiceParamResolver`와 `ParamProvider` 전략 패턴으로 메뉴별 파라미터 변환, 후보 추천, DB 검증 책임 분리
- 필수 파라미터 누락 시 재질문하고 후보가 있으면 유사 값을 추천하는 흐름 설계
- `MenuPermissionService`를 통한 사용자 권한 확인과 `VoiceLogService`의 비동기 로깅 구성
- `NAVIGATE`, `MISSING_PARAMS`, `RECOMMEND`, `SUMMARY`, `UNKNOWN` 등 상태 기반 응답으로 UI 처리 분기

#### 기술적 고려 사항
LLM의 추론 결과를 그대로 업무 처리에 사용하지 않고, 파라미터 보완·DB 결과 확인·사용자 권한 검증을 별도 단계로 구성했습니다. 메뉴별 파라미터 처리 책임을 분리해 신규 업무 유형을 추가할 수 있도록 했습니다.

### 2.8 JEUS/Miplatform Protocol Adapter 직렬화 장애 분석

- **기간:** 2024 ~ 2025
- **역할:** 장애 재현, 실험 환경 구성, 직렬화 문제 분석
- **기술:** Java, JEUS7A, Miplatform, MciResponse, DataSet, WebArgumentResolver, Protocol Adapter

#### 문제 및 수행 내용
- 특정 고객 데이터에 공백 또는 보이지 않는 문자가 포함될 때 운영 환경에서 Protocol Adapter 오류가 발생하는 현상 분석
- 로컬에서는 재현되지 않는 환경 차이를 줄이기 위해 테스트 Controller와 케이스별 분기 구성
- `WEB → JEUS → Service → DB` 흐름을 단계별로 확인해 오류 발생 지점을 축소
- DTO 기반 `MciResponse.setList`와 Map 기반 변환 동작을 비교하고, `addRowBean`과 `addRowMap`의 직렬화 차이 확인
- NBSP, ZWSP, 제어문자, DataSet 컬럼 구조, 정렬 순서 및 버퍼 옵션의 상호작용 점검

#### 결과
운영 장애를 실험 환경에서 재현 가능한 시나리오로 정리하고, 비표준 문자와 직렬화 방식의 상호작용을 기준으로 대응 방향을 마련했습니다.

- **KSNET 가상계좌 입금 서버 운영 환경 보완 (2026):** Java 1.8 빌드·실행 구조와 NSSM Windows Service 환경 정비. DB 전환은 실제 완료 범위를 확인해 설명

## 4. 면접에서 강조할 핵심 메시지

1. **업무 흐름을 이해하는 백엔드 개발자:** API 호출 자체뿐 아니라 상태 확인, 재처리, 데이터 정합성까지 고려해 업무 프로세스를 구현했습니다.
2. **원인을 재현해 좁혀가는 문제 해결 방식:** 운영에서만 발생하는 직렬화 장애를 실험 환경과 케이스별 테스트로 분석했습니다.
3. **보안과 공통 구조를 함께 고려:** 토큰/MFA/사용자 권한을 업무 흐름과 연결하고, 화면 노출과 서버 측 인가를 구분했습니다.
4. **레거시를 단계적으로 현대화:** 기존 업무 흐름을 고려해 화면·공통 설정·API 처리 구조를 점진적으로 정비했습니다.
5. **새 기술을 업무 문제에 적용:** LLM의 결과를 그대로 실행하지 않고 파라미터 보완, DB 검증, 권한 확인 및 로그를 결합했습니다.
